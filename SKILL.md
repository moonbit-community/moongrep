# moongrep

`moongrep` is an experimental structural search and taint-analysis tool for
MoonBit source code.

## Commands at a glance

| Command | Purpose |
| --- | --- |
| `moongrep lint` | Check a project with the embedded builtin rules. |
| `moongrep scan` | Run structural search or YAML rules across MoonBit files. |
| `moongrep dump` | Inspect the untyped CST for a MoonBit expression or top-level item. |
| `moongrep docs` | List or print the embedded English specifications. |

The examples below assume an installed `moongrep` executable. To run the
WebAssembly CLI instead, replace `moongrep` with:

```bash
moonx moonbit-community/moongrep --
```

## Quick start

### Lint the current project

Run the embedded builtin rules against the current directory:

```bash
moongrep lint
```

`lint` accepts all `scan` options, so you can combine builtin rules with custom
rules, filter findings, or switch to JSON output.

### Run a structural search

Run `scan` from the root of a MoonBit project with `--pattern` to search by
expression structure. By default, `scan` traverses directories recursively and
skips directories generated by Git and the MoonBit toolchain.

For example, to find `match` expressions that handle `Option` values:

```bash
moongrep scan --pattern 'match $(value:exp) { Some($(some:id)) => $(some_body:exp); None => $(none_body:exp) }'
```

Because `moongrep` streams results as it scans, pipe long output into a pager
such as `less -R`:

```bash
moongrep scan --pattern 'match $(value:exp) { Some($(some:id)) => $(some_body:exp); None => $(none_body:exp) }' | less -R
```

## Expression patterns and metavariables

`moongrep` parses both the search pattern and the target MoonBit source into
untyped concrete syntax trees (CSTs) and compares their structure:

- Ordinary MoonBit syntax in a pattern acts as fixed structure.
- Metavariables match and capture syntax nodes at their position.
- Formatting differences such as line breaks and indentation generally do not
  affect matching.

### Metavariable syntax and kinds

Write a typed metavariable as:

```text
$(name:kind)
```

`name` records the matched code under that name, and `kind` restricts which
syntax category can match:

| Kind | Matches |
| --- | --- |
| `exp` | A complete expression (variable, call, field access, `if`, etc.). |
| `id` | An identifier (variable name, parameter name, pattern binder, etc.). |
| `const` | A literal constant (integer, string, Boolean, etc.). |
| `arg` | A complete function-call argument (positional, labelled, or optional). |
| `pat` | A complete pattern. |
| `type` | A complete type. |

### Walkthrough example

Consider a pattern that matches a `match` expression with `Some` and `None`
branches:

```moonbit
match $(value:exp) {
  Some($(some:id)) => $(some_body:exp)
  None => $(none_body:exp)
}
```

Each placeholder captures one part of the expression:

- `$(value:exp)` captures the scrutinee expression.
- `$(some:id)` captures the identifier bound inside `Some(...)`.
- `$(some_body:exp)` captures the `Some` branch expression.
- `$(none_body:exp)` captures the `None` branch expression.

Against this source code:

```moonbit
match load_user() {
  Some(user) => display(user)
  None => show_error()
}
```

The match succeeds with these captures:

```text
value     = load_user()
some      = user
some_body = display(user)
none_body = show_error()
```

Fixed syntax must still match:

- A `match` with `Ok` and `Err` branches does not match because `Some` and
  `None` are fixed.
- `Some(1)` does not match `Some($(some:id))` because `1` is a constant rather
  than an identifier.

### Repeated metavariables and `$_`

Using the same named metavariable more than once requires all occurrences to
agree according to their kind:

- `id` compares normalized names.
- `const` compares parsed constants.
- CST-valued kinds (`exp`, `arg`, `pat`, `type`) compare syntax-tree structure
  while ignoring source locations.

For example:

```moonbit
$(value:exp) == $(value:exp)
```

This matches `user.name == user.name`, but does not match
`user.name == other.name`.

To match any node at a position without recording a capture, use the discard
placeholder `$_`. Multiple `$_` placeholders in the same pattern are
independent.

## Pattern guards

Use `--guard` to filter values captured by metavariables in a `--pattern`. For
example, to find `inspect` calls whose expected string is numeric:

```bash
moongrep scan \
  --pattern 'inspect($_, content=$(str:const))' \
  --guard '{$str: "^-?(0|[1-9][0-9]*)(\\.[0-9]+)?$"}'
```

### Syntax and quoting

Pass `--guard` as a YAML map, normally right after the `--pattern` it filters:

```text
--pattern '...$(name:id)...$(value:const)...' \
--guard '{$name: "regular expression", $value: "regular expression"}'
```

- Keys must be named metavariables declared in the pattern and must keep the
  `$` prefix.
- Values must be regular-expression strings.
- Wrap the YAML map in single quotes so the shell does not expand `$name`, and
  wrap each regex in double quotes.
- Escape backslashes inside double-quoted YAML strings (write `\.` as `\\.`).

### What guards can check

- **Supported kinds**: `id` and `const` captures only. Guards cannot filter
  `exp`, `arg`, `pat`, `type`, ellipsis captures, or `$_`.
- **Compared text**:
  - For `id`, the regex matches the normalized identifier (for example `name`
    or `@pkg.name`).
  - For `const`, the regex matches the parsed constant value (for example
    `"raw"` becomes `raw`, `42` becomes `42`, and `true` becomes `true`).
- **Matching behavior**: Regexes use substring matching by default (so `"raw"`
  also matches `"draw"`). Use `^` and `$` to match the full value (for example
  `"^raw$"`).
- **Combining conditions**: All entries in one guard map must match (logical
  AND). Each `--pattern` accepts at most one `--guard`; pair `--pattern` and
  `--guard` to filter multiple patterns.

Example constraining both callee and argument:

```bash
moongrep scan \
  --pattern '$(callee:id)($(value:const))' \
  --guard '{$callee: "^@html\\.render$", $value: "^(danger|raw)$"}'
```

## Structured output (`--json`)

By default, `moongrep` writes human-readable output. Pass `--json` to emit
compact JSON Lines for coding agents and scripts:

```bash
moongrep scan --pattern 'inspect($_, content="true")' --json
moongrep dump --json --expr 'x + 1'
```

### Stream contract

- Every nonempty application-output line is one compact JSON object.
- **Standard output**:
  - `scan` and `lint`: only `finding` records (empty when there are no hits).
  - `dump`: one `dump` record on success (unless `--exit-code` is set).
- **Standard error**: only `trace`, `warning`, and `error` records.
- Records stream in traversal order; a later failure does not withdraw records
  already printed.
- A standalone `--json` on `scan`, `lint`, or `dump` is detected before full
  argument parsing, so usage errors also print as JSON. `--json` after `--` is
  not treated as an option. Successful help output stays plain text.

### Record shapes

```text
finding: { "type":"finding", "file", "rule_id", "description", "range",
           "matched_source", "source_context" }
warning: { "type":"warning", "category", "message", ...details }
trace:   { "type":"trace", "event", ...event fields }
dump:    { "type":"dump", "kind":"impl"|"expr", "content" }
error:   { "type":"error", "category", "exit_code", "message",
           ...optional diagnostic fields }
```

- **Warning categories**: `parse`, `invalid_skip_payload`, `taint_incomplete`
- **Trace events** (`--verbose`): `rule_loaded`, `directory_entered`,
  `path_skipped`, `file_started`
- **Error categories**: `internal`, `usage`, `dump_input`, `rule_source`,
  `rule_content`, `scan_input`, `output`, `taint_incomplete`

## Inspecting CSTs (`dump`)

Use `dump` to print MoonBit `untyped_cst` debug output or validate pattern
syntax:

```text
moongrep dump [--exit-code] [--strict-check] [--json] (--impl <impl> | --expr <expr>)
```

Examples:

```bash
moongrep dump --impl 'fn answer { 42 }'
moongrep dump --expr 'x + 1'
moongrep dump --json --expr 'x + 1'
moongrep dump --exit-code --expr 'x + 1'
moongrep dump --strict-check --impl 'fn wrapper { __TARGET__ }'
```

### Options

- `--impl <impl>`: Parse one MoonBit top-level implementation item and print
  its `untyped_cst` debug representation. Mutually exclusive with `--expr`.
- `--expr <expr>`: Parse one MoonBit expression and print its `untyped_cst`
  debug representation. Mutually exclusive with `--impl`.
- `--strict-check`: Run the extra pattern validation used by `scan` after the
  initial parse succeeds. `--expr` is validated as an ordinary structural
  pattern; `--impl` is validated with default `inside-toplevel` semantics and
  must contain exactly one bindable expression position named `__TARGET__`.
  Does not change successful text or JSON output.
- `--json`: Write one single-line JSON `dump` record (`type`, `kind`, and
  JSON-escaped `content`).
- `--exit-code`: Validate without printing the CST. On success, writes nothing
  to stdout or stderr and exits with `0` (even with `--json` or
  `--strict-check`). Invalid syntax exits with `3`; a failure raised only by
  `--strict-check` exits with `5` (`invalid dump pattern`). With `--json`,
  either failure uses the standard JSON `error` schema.

Running `moongrep dump` with no arguments prints `dump` help and exits `0`.
Usage errors (such as passing both `--impl` and `--expr`, or `dump --json` with
no input) exit `2`; `dump --json --help` prints ordinary help and exits `0`.

## Exit status

`moongrep` exits with `0` for help, successful `dump`, scans with findings,
scans with no findings, and scans with recoverable warnings. It does not use
grep-style exit code `1` for no-match scans.

| Code | Meaning |
| ---: | --- |
| `0` | Success (including no-match scans and recoverable warnings). |
| `1` | Internal or unclassified error, including damaged builtin rules. |
| `2` | Command-line usage error. |
| `3` | Invalid `dump` input (lexical or parse failure). |
| `4` | Missing, unreadable, or wrongly typed rule source, or a rule directory with no `.yaml` / `.yml` files. |
| `5` | Invalid rule content (blank/invalid YAML, unsupported single-file `--rule` suffix, invalid schema, pattern, guard, or compiled rule) or invalid `--strict-check` dump pattern. |
| `6` | Missing or unreadable scan input. |
| `7` | Standard-output or standard-error write failure. |
| `8` | Incomplete taint analysis when `--strict-taint` is enabled. |
